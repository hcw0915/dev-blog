> 每個有點規模的前端專案，都會長出一個處理後端錯誤碼的地方。它一開始是三個 `case`，兩年後變成一個沒人敢動的巨型 `switch` —— 因為你不知道刪掉某一行，會不會有某個角落的功能就此失去提示。這篇記錄一種把它拆開的做法：**請求層只負責廣播，誰關心哪個碼誰自己認領**。

## 心智模型：單向廣播 + 多方認領

核心規則只有一條：**發送請求的那一層，不渲染任何 UI**。

它只做一件事 —— 把後端回傳的錯誤碼翻譯成一個事件，廣播到 `window` 上。至於「這個碼該彈什麼」，由各方監聽器自己決定。

```js
// 派發端：只廣播，不決定 UI
const ERROR_EVENT = "app:error-code"

window.dispatchEvent(new CustomEvent(ERROR_EVENT, {
  detail: { status, params }
}))
```

這個轉向帶來的實際差別是：**新增一個錯誤碼，不再是「去那個大檔案裡加一個 case」，而是「決定它歸哪一類、由誰認領」**。前者所有人改同一個檔案，後者各自改各自的模組。

## 兩種事件，兩種 detail 形狀

只需要兩條通道：

| 事件 | detail 內容 | 用途 |
|---|---|---|
| toast 類 | 文案描述物件（或字串） | 單純彈一句提示 |
| code 類 | `{ status, params, errorUrl }` | 交給業務端按碼認領 |

分成兩種而不是一種，是因為它們的消費方式不同：toast 類的 detail 已經是最終文案，收到就直接顯示；code 類的 detail 是**原始狀態**，收到的人要自己判斷這是不是自家的碼。

兩種 detail 形狀不能混 —— 這是實作時最容易搞錯的地方。

## 三個實作上必須注意的點

**一、伺服器端不派事件。** 派發端要先判斷 `typeof window !== "undefined"`，否則 SSR 階段會直接炸掉。

**二、全域監聽必須是單例。** 掛在應用初始化元件的 `useEffect([])` 裡、卸載時解綁。如果這個元件不小心有兩個實例，使用者會看到兩次一模一樣的 toast —— 而這種 bug 查起來特別慢，因為程式碼看起來完全正確。

**三、處理完之後仍要 re-throw。** 請求層在 catch 裡分流完錯誤，必須把原始錯誤重新拋出。這是後面「旁路處理」能成立的前提 —— 呼叫方的 catch 仍然拿得到完整的錯誤物件，可以做第二次處理。

## 認領怎麼做：stopImmediatePropagation

業務模組自己掛監聽，只認領自家關心的碼：

```js
const OWNED_CODES = [/* 這個模組關心的幾個碼 */]

const handler = event => {
  const status = event.detail?.status
  if (!OWNED_CODES.includes(status)) return   // 不是自家的碼，放行
  event.stopImmediatePropagation()            // 是自家的，攔下
  openDialog(/* … */)
}
window.addEventListener(ERROR_EVENT, handler)
```

`stopImmediatePropagation()` 是這個模式的關鍵 —— 它阻止同一個事件上的其他監聽器繼續執行，包含那個全域的預設處理器。沒有它，使用者會同時看到「業務彈窗」跟「全域 toast」兩個提示。

但光靠它還不夠。全域的預設分支也必須**顯式排除**那些已被認領的碼，因為認領方可能在全域監聽器之後才掛上去。**兩邊都要改，這是這個設計的代價。**

## 五種模式與它們的優先序

分流本身是一條 if-else 鏈，命中即 return，所以順序就是優先序：

| 順位 | 模式 | 判定 | 出口 |
|---|---|---|---|
| 1 | 忽略（交給業務認領） | 在「忽略清單」裡 | code 事件 |
| 2 | 帶參數的提示 | 在「特殊清單」裡 | toast 事件（文案含變數） |
| 3 | 登入失效 | 特定幾個碼 | code 事件 → 完整登出鏈 |
| 4 | 一般提示 | 以上皆非（預設） | toast 事件 |
| 5 | 特定流程專屬彈窗 | 不進總線，走 re-throw 之後的 catch | 直接開彈窗 |

第 5 種值得特別說：它是**旁路**，不走總線。用途是「同一個錯誤碼，在登入流程裡要彈一個專屬引導，但在其他 API 呼叫時不該彈」。因為總線是全域的，沒辦法表達「只在某個流程裡」這種條件，所以這類需求只能走 re-throw 之後的 catch。

「帶參數的提示」那一類也值得一提：後端把變數（金額、剩餘次數、鎖定分鐘數）放在錯誤回應的參數陣列裡，前端按碼查映射表決定哪個位置對應哪個變數，填進多語系文案。這讓「您今日還可提領 $500」這種文案不必寫死在程式碼裡。

## 已知陷阱

這套機制跑了一段時間後，累積的坑比設計本身更值得記：

**優先序會讓設定悄悄失效。** 一個碼如果同時被加進「忽略清單」和「特殊清單」，因為忽略的優先序較高，它實際上永遠走忽略那一檔 —— 你在特殊清單裡登記的參數映射完全不會執行，而且不會有任何錯誤提示。改清單前一定要交叉核對。

**翻譯缺漏只會回退成「[碼] 未知錯誤」。** 新增錯誤碼時忘了補多語系字串，使用者看到的就是一個數字加「未知錯誤」。這是所有錯誤碼機制的共同弱點：程式碼改動與文案改動在不同的地方，沒有任何東西會檢查它們是否對齊。

**錯誤監控會被業務錯誤淹沒。** 如果請求層在 catch 裡一律送出例外上報，那些「未完成身分驗證」之類的正常業務流程錯誤也會全部進去。這不是 bug，但它會讓真正的例外被埋掉，必須在監控端另外過濾。

**不是所有錯誤都走這條總線。** 有些介面把業務子碼放在回應的 `data` 裡而不是錯誤碼裡，由對應的模組直接讀欄位判斷，完全不經過這套機制。維護時要意識到這一點，否則會在清單裡找一個根本不在裡面的碼。

**跨框架的錯誤要重放。** 如果站上有嵌入的 iframe 頁面，它裡面發生的登入失效不會自動觸發外層框架登出 —— `window` 事件不跨 frame。解法是 iframe 內把錯誤 `postMessage` 回主框架，主框架收到後重放同名事件，讓它重新進入同一條總線。

## 什麼時候值得這樣做

這個模式的成本很實在：多了一層間接、除錯時要追事件而不是追函式呼叫、認領與全域排除兩邊都要改。

值得的訊號是：**你的錯誤處理檔案開始有人不敢動了**。當「加一個錯誤碼」變成要去讀完整個 switch 才敢下手，或者兩個團隊的功能在同一個 case 裡打架，那就是該把決定權還給各模組的時候。

反過來說，如果你的錯誤碼只有十幾個、都只是彈一句提示，那一個 switch 就夠了 —— 不要為了架構而架構。
