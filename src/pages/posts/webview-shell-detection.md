> 同一份網頁程式碼，會被塞進純瀏覽器、PWA、iOS 與 Android 的 WebView、React Native 的 WebView、TWA、Cordova、Flutter，還有各家社交 App 的內建瀏覽器與手機廠商的商店包裡執行。前端必須先回答「我現在在什麼殼裡」，才能決定接下來的行為。這篇記錄這套偵測怎麼做、判斷完之後有哪些行為要分叉，以及一個沒收好的判定邏輯最後會付出什麼代價。

> [!NOTE]
> 作者說明：這套容器偵測與原生橋由團隊多位同事陸續累積而成。我補過 iOS 原生橋的修正與新商店包的判定，這篇是我維護時整理的全貌。

## 為什麼非判不可

「我在什麼殼裡」不是一個學術問題，它直接決定好幾件事能不能正常運作：

- **外部連結**：WebView 裡 `window.open` 開新頁，要麼被殼吞掉、要麼開在 WebView 內部回不去，所以必須交給原生層用系統瀏覽器打開。
- **登入態同步**：原生殼裡要把 token 與語系推給 native。
- **效能**：某些 WebView 裡 `requestIdleCallback` 根本不會觸發，靠 idle 排程的延後掛載會永遠等不到。
- **功能裁剪**：殼包內要隱藏第三方登入入口；社交 App 的內嵌瀏覽器裡要引導使用者改用系統瀏覽器開啟。

## 兩層信號，不要混用

偵測靠兩層信號，它們的可信度完全不同：

| 信號 | 怎麼來 | 拿來做什麼 |
|---|---|---|
| **推斷欄位** | UA 字串 + 網址參數 + standalone 狀態算出來 | 行為分支判斷 |
| **注入物件** | native 真的注入在 `window` 上的物件 | 真正要發送橋訊息時 |

這個分界很重要：**推斷欄位回答的是「我大概在什麼殼」，注入物件回答的是「native 確實在」。** 要發訊息給原生層時一定要嗅探實際的注入物件，不能只信推斷欄位 —— 推斷可能是對的，但注入還沒完成，訊息就會掉進黑洞。

## UA 嗅探：有 WebKit 沒 Safari

iOS 這一側的判定，核心是一條負向先行斷言：

```js
const isIOSWebView =
  isIOS && /(iPhone|iPod|iPad).*AppleWebKit(?!.*Safari)/i.test(ua)
```

原理是：系統 Safari 的 UA 裡帶有 `Safari` 這個 token，而 App 內嵌的 WebView 用的是同一套 WebKit 引擎、卻不會帶上這個後綴。所以「有 WebKit、沒有 Safari」就等於這是個殼。

這條規則好用，但它也提醒了 UA 嗅探的本質：**你是在用「缺少什麼」反推環境**，而不是環境主動告訴你它是誰。這種判斷天生脆弱，所以它只能當第一層，不能當唯一一層。

## 三種原生橋，形狀都不一樣

判斷完之後，要跟原生層說話。三種主要容器的通道長得完全不同：

| 容器 | 呼叫方式 | 參數形態 |
|---|---|---|
| React Native | `window.ReactNativeWebView.postMessage(...)` | JSON 字串 |
| iOS WKWebView | `window.webkit.messageHandlers.<name>.postMessage(...)` | JSON 字串 |
| Android | `window.<bridge>[cmd](params)` | **函式表**，不是 postMessage |
| Flutter | `callHandler(...)` | JSON，而且欄位名用 `action` 不是 `cmd` |

Android 那一行是最容易踩的：它**不是 postMessage，而是一張函式表**，指令名稱得跟 native 端逐字對齊 —— 同一個指令寫成 camelCase 還是 snake_case 是兩件事，而錯的那種不會報錯，只會什麼都不發生。Flutter 那條通道又把欄位名從 `cmd` 換成 `action`，兩套互不相容。

所以中間一定要有一層抽象：每次呼叫前重新嗅探 window 上有哪個注入物件，按優先序決定走哪條通道，消費端只管送指令。

**這裡有個必須知道的失敗模式**：等待 native 注入通常是用輪詢（例如每秒一次、最多五次），輪詢用完還沒等到，環境就會被標成未知，之後**所有呼叫靜默失敗** —— 不會拋錯、不會有紅字，前端也無從得知 native 到底收到沒有。要嘛接受這個代價，要嘛自己加一層明確的逾時回報。

## 判斷完之後，下游要分叉什麼

偵測本身只是手段，真正的複雜度在消費端：

- 外部連結改走原生橋，而不是 `window.open`
- 偵測到某些 WebView 時跳過 idle 排程，直接掛載（因為那裡 idle 回呼不觸發）
- 關閉原生的啟動畫面
- 每次 API 與 WebSocket 請求帶上容器類型與作業系統類型
- 殼包內隱藏第三方登入
- 社交 App 內建瀏覽器裡顯示「用瀏覽器開啟」的引導

一個推斷欄位，牽動二十幾個消費點。**這就是麻煩的起點。**

## 真正的教訓：判定邏輯漂移

這套機制最值得寫下來的，不是它怎麼偵測，而是它怎麼壞掉的。

「算出殼身分」這件事，被**重複實作了三份**，而且三份的條件已經不一致了。具體的症狀是：同一個網址參數進來，其中一份把它判成「自家原生殼」，另一份判成「外部 App」，兩者對同一個問題給出相反的答案。

而三份都會在啟動流程裡跑到，前後覆寫，所以 **最終值取決於誰最後寫**。這不是隨機的 bug，是必然的 —— 只要有兩個地方在算同一件事，它們遲早會分岔。

更細一層的坑：專案裡有**兩個同名的判定函式**，一個有裝置類型守門、一個沒有，所以桌機瀏覽器的 PWA 在其中一個裡會被認成 PWA、另一個裡不會。改了其中一處而沒改另一處，行為就會不一致。

消費端的情況更糟：二十幾個檔案在讀殼身分，但用的口徑有四到五套不同的集合 —— 有的直接讀某個布林欄位、有的自己列舉一組類型、有的判斷社交殼名稱。**沒有任何一個函式叫「這是不是殼」。** 每個新需求進來，開發者找不到標準答案，就再拼一套自己的集合，於是集合數量只增不減。

## 可以帶走的三條

**一、推斷與實證要分開。** 用 UA 推斷出來的欄位只配拿來做行為分支；真要跟原生層通訊，一定要嗅探實際注入的物件。把這兩件事混成同一個欄位，就是在賭注入時序。

**二、同一件事只能有一個地方算。** 判定邏輯散在三處、又都在啟動流程裡覆寫彼此，最終值就由執行順序決定 —— 這種 bug 無法靠讀單一檔案找出來，只能靠人記得「還有另外兩處」。而人會忘記。

**三、給判定一個有名字的函式。** 差別不在程式碼量，而在**新人有沒有標準答案可抄**。沒有 `isNativeShell()` 這種東西，每個人就會自己拼一套集合，然後這些集合會各自演化。等到有二十幾個消費點時，收口的成本已經高到沒人敢動。

最後一個容易混的地方：**響應式斷點跟底層容器偵測是兩條完全不同的線**。「螢幕是不是窄的」跟「我是不是在原生殼裡」沒有因果關係 —— 用容器偵測的結果去做版面斷點，或反過來用斷點去判斷容器，都會在某個組合下出錯。這兩件事從一開始就該用不同的來源。
