> 臨時除錯程式碼有個共通命運：寫的時候很快，用完沒刪，下次要用又得改一次程式碼。這篇記錄把它們收斂成一套站內面板（我們叫它 dev-panel）的設計取捨 —— 面板怎麼開、進入點該下在哪、以及怎麼確保正式包裡完全看不到它。

![面板首頁：11 支模組分三組](/posts/dev-panel_01-modules.png)

## 為什麼臨時除錯碼總是留不住也刪不掉

先描述問題。一個中型前端專案裡，除錯需求通常長這樣：

- 想看某個元件換一套樣式檔位長怎樣 → 手動改 props，看完改回來
- 想驗證收到某個 websocket 推送之後整站的反應 → 自己造一筆假資料塞進去
- 想預覽登入流程的第 14 種狀態 → 在版型裡加一行 JSX，看完註解掉

這三件事的共通點不是「寫得爛」，而是**啟用除錯的操作等同修改程式碼**。於是會發生兩件必然的事：

1. 用完忘了刪，程式碼裡長期躺著一段被註解掉的面板。
2. 沒忘記刪，但某次跟著功能一起提交上去了。

我遇過的最明確的訊號是第二種：某個為了預覽表單而加的一行 JSX，被誤提交過兩次。這不是誰粗心，是機制問題 —— 只要「開啟除錯」需要動到檔案，它就一定會在某次 commit 裡混進去。

把它工具化的價值不在功能多，而在**把除錯從「改程式碼」變成「加一個網址參數」**。

## 開關：兩個條件都要成立

```ts
const isDevPanelEnabled = () => {
  if (enabled !== null) return enabled;
  if (process.env.NEXT_PUBLIC_ENV !== "dev" || typeof window === "undefined") return false;

  enabled = new URLSearchParams(window.location.search).get("dev_panel") === "1";
  return enabled;
};
```

開發環境**加上**網址參數，缺一不可。少了參數，平常開發時面板不會擋路；少了環境判斷，正式站被人猜到參數就會開出來。

結果快取在模組層級的變數裡，因為每個主要元件在 render 時都會問一次，不該每次重新解析 query string。

儲存也刻意隔離：面板狀態一律走 `sessionStorage`，而且用自己的 key，不進正式程式碼共用的那份 key 列舉。理由有兩層 —— 除錯工具往正式程式碼的列舉裡塞東西，本身就是一處侵入；而除錯用的覆寫「關掉分頁就該消失」，不該跟著人到下一次開站。

## 注入點：4 個，而且都是唯一出口

面板要能改變頁面行為（換站台身分、換版面順序、換元件樣式、預覽表單），就得在正式程式碼裡留進入點。這是整件事最需要克制的地方：**進入點越多，正式程式碼被除錯邏輯污染得越嚴重**。

最後只留四個，每個都選在「這份資料的唯一出口」：

| 注入的位置 | 覆寫什麼 |
|---|---|
| 版面組合的客戶端元件 | 版面順序 |
| 執行期的元件渲染器 | 元件樣式檔位 |
| 站台設定的 provider | 站台身分（合規與否、審核模式） |
| 登入版型 | 表單狀態預覽 |

四處的寫法完全一致：

```tsx
// 沒開面板時原樣回傳，正式環境等同不存在。
// 訂閱版本號是為了讓面板改完即時生效 —— 面板沒開時這個 store 永遠不會變動。
useDevVersion();
const data = applyDevOverride(original);
```

選位置的判準是「**這份資料全站從哪裡出去**」。站台身分那一處特別明顯：整站的合規判斷、審核模式、登入模板全都從同一個 context 出去，所以覆寫只需要掛在那一個出口。版面順序同理 —— 底下的高度預估、阻塞資料、渲染計畫全部由那份陣列派生，改它等同後端改了下發順序。

選對位置，一個注入點就夠；選錯位置，就要在十個地方各補一次，然後漏掉第十一個。

![站台身分：多國 × 合規／非合規／審核模式，下半把建置期設定與後端設定並排](/posts/dev-panel_03-site.png)

這一頁也解釋了為什麼站台身分值得獨立做：**建置期的設定與後端下發的設定是兩半**，過去要靠人工核對兩邊有沒有對上。面板把「實際生效的值」與兩邊來源並排列出來，一次切換就不會出現「前端旗標改了、後端的國別代碼沒改」這種半套狀態。

## 一個會靜默失效的坑：就地改寫 vs 回傳副本

覆寫元件樣式時，直覺寫法是「回傳一個改過的副本」。這在這個專案裡會**靜默失效**，原因是兩個上游行為疊在一起：

1. 帶客戶端取數的元件，在資料回來後會做 `{ ...props, ...fetched }` —— 這個展開會**蓋掉上游傳進來的副本**。
2. 它的取數快取以元件 id 為鍵、不含樣式 —— 所以切換樣式檔位不會觸發重新取數。

結果是：面板顯示已套用、畫面完全沒變、也不會報錯。只有部分元件受影響（純靜態的正常、帶取數的失效），所以更難察覺。

改成就地改寫就解決了。這個坑的一般化教訓是：**覆寫值之前，要先確認資料在你之後還會不會被重新組裝**。展開運算子很常見，而「後面那個蓋掉前面那個」正是它的定義。

![元件樣式表：可切換樣式檔位、拖拉換序、展開後端下發的原始 JSON](/posts/dev-panel_02-component.png)

## 掛載：面板必須待在框架的模組圖裡

理想掛法是零侵入：掛在框架原生的客戶端入口，完全不碰任何業務元件。

試了，Turbopack 編不過。原因是面板會 import 彈窗註冊表，而那份註冊表的 loader 指向 `app/` 底下的模組；從非 `app` 入口去建那些 chunk，打包器會直接報錯。

結論是**面板必須待在 app graph 裡面**，所以改掛在一個既有的客戶端初始化群組底下：

```tsx
const DevPanel =
  process.env.NODE_ENV === "development"
    ? dynamic(() => import("@/components/features/dev-panels"), { ssr: false })
    : () => null;
```

關鍵是 `process.env.NODE_ENV === "development"` 這個**字面量分支**：正式建置時它是常數 false，整條分支連同底下的動態 import 會被搖掉，chunk 不會進正式包。

面板集合內部還有第二層。皮膚切換那一支會 import 全部十幾套皮膚的 CSS（切換時需要它們在頁面上），所以它自己再切一個 chunk、一樣用環境變數包住。這一層用 **React 原生的 `lazy` 而不是框架的 `dynamic`** —— 那段程式碼在面板集合內部，用 React 自己的機制就不必把打包器的路由圖牽扯進來。

## 配色：要的不是「跟著主題」，是「跟主題相反」

面板的強調色取當前皮膚主色的**互補色**（色相 +180°）。

會這樣做是因為第一版直接吃了主題色，結果很糟：黃底站台配出黃色面板、綠底站台配出綠色高亮，面板跟頁面糊成一片。**除錯工具最該做到的是「一眼看出這不是頁面的一部分」**，所以要的不是協調，是對比。

實作上只轉色相，飽和度與亮度一律釘在「深底上看得清」的那一檔。因為主色有的很暗有的很淡，照抄原本的 S/L 會得到在深色面板上讀不出來的字。

還有兩個邊界要處理：

- 主色接近灰階時，互補色沒有意義（轉 180° 還是同一個灰），這時直接不設，讓它落回預設的洋紅。
- 而洋紅是實測所有皮膚後挑的 —— **沒有任何一套用到 290–310° 這段色相**，所以就算算不出互補色，也不會跟頁面撞色。

![皮膚 / 主題 / 語言：十幾套皮膚、數套主題與語系一覽](/posts/dev-panel_04-skin.png)

這一頁還有個分寸值得記：皮膚與主題**只改根元素上的屬性，重整就回到原本的設定**，所以不會污染狀態。但換語言不同 —— 它要走整頁導航，不是改屬性，面板就照實標示，不假裝它們是同一種操作。本站沒開的語系標成灰底並註明點了會 404，而不是讓人踩下去才發現。

## 探針：自訂屬性的值不是顏色

要算互補色，得先拿到主色的 RGB。這裡有個會讓整套機制悄悄失效的陷阱，而且不限於這個專案：

**CSS 自訂屬性的 computed 值是「原樣的字面量」。** 樣式檔寫 `#31ed87`，`getComputedStyle` 讀回來就是字串 `#31ed87`，不是 `rgb(...)`。如果直接用正規表達式抓數字，會抓到 `31` 和 `87` 兩段，判定成「不是顏色」，然後每套主題都算出同一個 fallback。

解法是讓瀏覽器幫你正規化：丟進一個隱藏元素的 `color`，再讀回來。

```ts
const probe = document.createElement("span");
probe.style.display = "none";
probe.style.color = declared;   // 塞進去的是字面量
document.body.appendChild(probe);
const rgb = getComputedStyle(probe).color;  // 讀回來就是 rgb(r, g, b)
probe.remove();
```

元素檢視的 token 反查用的是同一招：掃根元素上所有自訂屬性、逐一正規化，建成「顏色值 → token 名稱」的對照表，於是滑過任何元素都能顯示它用的是哪個 token，而不只是一組色碼。

![元素檢視：margin 橘 / padding 綠 / content 藍，數值寫在色塊裡，並反查出對應的 token](/posts/dev-panel_08-inspect.png)

但長度類的 token（圓角、間距）**刻意不繞這一層**，直接比字面值。繞過去反而會把 `6px` 和 `0.375rem` 判成不同的東西 —— 同一個技巧不是到處都適用。

還有一個位置問題：這些 CSS 變數掛在根元素而不是面板節點上。因為元素檢視的浮層是 portal 到 `body` 的，掛在面板上它讀不到。

## 幾個「照實說」的設計

面板做久了會發現，**誠實標示限制比假裝全能更有用**。三個例子：

### 彈窗：參數骨架由型別產出

![彈窗面板：數十支彈窗分組，點一支就帶出參數骨架](/posts/dev-panel_06-dialog.png)

彈窗數量到幾十支時，手寫一份參數範本，第一次改型別就會全部過期。所以骨架是**從型別定義產出**的。

而面板上直接標了一句「回呼類的不列（面板填不了）」—— 函式型別沒辦法用表單填。與其給一個填不了的欄位讓人困惑，不如寫明它不在這裡處理。

### 推送模擬：走真實的分發路徑

![websocket 推送模擬：數十種推送類型，可帶預設參數](/posts/dev-panel_07-websocket.png)

模擬推送不是「假造一個畫面」，而是**偽造一則訊息丟進真正的訊息處理函式，跑完整條分發邏輯**。驗的是「收到之後整站會怎樣」，不是「這個元件長怎樣」。

常用的類型還預先填好參數，不用每次自己查欄位。假造畫面只會騙自己，走真實路徑才驗得到鏈路反應。

### SEO：標明讀的是哪一份 DOM

![SEO / TDK：欄位一覽與分享卡預覽](/posts/dev-panel_05-seo.png)

這一頁刻意標明「讀的是 hydrate 之後的 DOM 現況，不是伺服器回包」。兩者可能不同，而社群平台抓的是回包 —— 所以面板另外畫了一個近似聊天軟體的分享卡預覽，讓人知道分享出去大概長什麼樣。

不標的話，看到面板顯示正確就以為沒事，是最糟的情況。

## 相依方向決定它會不會漏進正式包

最後一個設計，是整套裡最容易做錯的：表單預覽要把內容塞進登入版型的內容區，不能自己浮在角落。這產生一個「誰 import 誰」的問題。

直覺做法是面板存一個識別字串，讓版型自己去 render 對應的表單。這樣做的代價是：**版型必須 import 那張表單對照表**，而那張表會把所有表單一起拉進來 —— 於是除錯用的東西就被釘進正式包了，因為版型是生產元件。

改成反過來：**面板把「已經渲染好的節點」推進共用狀態，版型只負責讀**。兩邊都不必 import 對方，而面板那側本來就有環境變數的閘門擋著。

這是可以帶走的通則：**相依方向決定 tree-shaking 能不能生效**。讓除錯側去 import 正式側，不要反過來。

## 小結

三個可以套用到別的專案的判斷：

1. **注入點要下在資料的唯一出口**，不是下在每個使用處 —— 選對位置，四個就夠涵蓋版面、樣式、身分、表單。
2. **除錯工具要看起來不像頁面的一部分** —— 配色取對比而不是協調，這樣才不會把面板誤認成頁面。
3. **相依方向決定它會不會漏進正式包** —— 除錯側可以 import 正式側，反過來就會把整包拖進去。

至於值不值得花這個工：被收掉的那幾段臨時程式碼裡，有一段被誤提交過兩次。工具化之後，「用完忘了刪」這件事在機制上就不會發生了。
