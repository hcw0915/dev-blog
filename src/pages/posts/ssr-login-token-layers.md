> 登入成功、拿到 token 之後，它該存在哪裡？在純客戶端渲染的應用裡這題很單純，但只要加上伺服器端渲染，`localStorage` 這個最直覺的答案就有一半時間不存在。這篇記錄一套三層落地的設計：每一層各自解決什麼、為什麼伺服器端只讀得到其中一層，以及這個設計留下的三個缺陷。

## 先說結論：三層各司其職

| 層 | 存什麼 | 誰讀 | 寫入 |
|---|---|---|---|
| 執行期 store | token、是否登入、使用者 id | 元件執行時的真值來源 | 同步 |
| `localStorage` | token、使用者 id | 客戶端發 API 前取用 | 同步 |
| cookie | token、是否登入、少數輕量狀態旗標 | 伺服器端渲染、middleware、跨網域嵌入頁 | 非同步佇列 |

濃縮成一句話：**store 是執行期真值，`localStorage` 負責刷新後恢復，cookie 負責讓伺服器端與跨網域頁面也判斷得出登入狀態。**

三層聽起來冗餘，但拿掉任何一層都會壞掉一個情境：

- 只有 store：重新整理頁面就登出，因為記憶體狀態不跨頁面生命週期。
- 只有 `localStorage`：伺服器端完全讀不到，所有需要登入態的頁面都只能先渲染成未登入、等 hydration 之後再跳一次。
- 只有 cookie：每個請求都會把 token 帶上，而多數請求根本不需要它。

## 伺服器端那一層最容易誤解

這是整套設計裡最違反直覺的部分，值得單獨講。

**第一件事：伺服器端沒有 `localStorage`。** 這句話大家都知道，但它的連鎖後果常被低估 —— 它代表**伺服器端的 API 請求根本帶不到真 token**。我們的取值函式在 `window === undefined` 時直接回傳一個佔位字串，讓請求照樣送得出去，但拿不到個人資料；真正需要使用者資料的區塊，一律等 hydration 之後由客戶端再拉一次。

**第二件事：伺服器端其實不需要 token，它只需要一個布林值。** middleware 與路由門禁要回答的問題是「這個人登入了沒」，不是「他是誰」。所以 cookie 裡除了 token 之外，還單獨存了一個輕量的「是否登入」旗標，門禁只讀這個旗標做跳轉與分支。

這就解釋了一個乍看多餘的設計：**為什麼 cookie 裡要同時有 token 和一個布林旗標**。它們的讀者不是同一個 —— 布林旗標給伺服器端門禁，token 則是給跨網域嵌入的活動頁用 `document.cookie` 讀的，**不是拿來做伺服器端 API 鑑權**。

把取值路徑攤開會清楚很多：

| 誰要取值 | 從哪層取 | 取來做什麼 |
|---|---|---|
| 元件執行時 | 執行期 store | 真值來源 |
| 客戶端 API 請求 | `localStorage` | 真 token，帶進鑑權標頭 |
| 伺服器端 API 請求 | 取不到 | 回傳佔位值，不帶真 token |
| middleware／路由門禁 | cookie 的布林旗標 | 只判斷登入與否 |
| 跨網域嵌入頁 | cookie 的 token | 跨網域取用 |

## 兩個防競態的細節

設計裡有兩處是被實際問題逼出來的，不是一開始就想到的。

**原子寫。** token、是否登入、使用者 id 必須在同一次 `set()` 裡一起提交。分開寫的話，訂閱這個 store 的模組會在中間那一瞬間讀到「已登入但還沒有 id」的半更新狀態 —— 而這種狀態通常不會報錯，只會讓某個依賴 id 的請求安靜地送出錯誤參數。

**cookie 寫入佇列化。** cookie 的寫是非同步的（優先用 `cookieStore` API，不支援時退回 `document.cookie`），多次狀態變化並發寫會互相覆蓋。把寫入排成佇列，後一次等前一次完成，覆蓋問題就消失了。

## 多個登入入口，一個匯流點

這套系統有四種拿到 token 的方式：帳號密碼、第三方 OAuth（透過 iframe 的 `postMessage` 把憑證傳回主頁）、原生殼冷啟動時用網址參數直接登入、以及跨自然日或換裝置時用舊 token 換新 token。

它們拿 token 的路徑完全不同，但**成功之後全部匯進同一個保存函式**，再由它做三層落地。這是這套設計裡最省事的一個決定：新增一種登入方式時，只要負責「拿到 token」，不必再重寫一次保存邏輯，也不會有某個入口漏寫其中一層。

## 三個我們留下的缺陷

寫設計文件最容易的是只講對的部分。這套機制有三個已知問題，兩個是取捨、一個是真的沒做好。

**一、cookie 不是 httpOnly，這是刻意的妥協。** 因為 cookie 由客戶端寫入，它天生就不可能是 httpOnly —— 而這代表任何 XSS 都讀得到 token。同樣的原因，`secure` 與 `sameSite` 也沒設。正確的做法是把關鍵 token 改成由伺服器端下發的 httpOnly cookie，客戶端只留不敏感的部分。這件事我們知道，還沒做。

**二、token 同時存在 `localStorage` 和 cookie，雙寫就會漂移。** 兩份資料只要有任何一條路徑只更新其中一份，就會出現兩邊不一致，而且不一致時沒有任何機制會發現。比較健康的做法是收斂成單一來源，其餘視為派生值。

**三、登入後的收尾沒有串成明確的 await 鏈。** 這個最實際：登入成功後還有一串收尾動作（拉使用者資料、刷新各種狀態），其中有些是 fire-and-forget、沒有 await。結果是「已完成初始化」這個旗標可能在收尾動作還沒回來時就被設成 true。

更糟的是使用者資料的重試是硬上限 —— 兩次都拿不到就整段收尾放棄，但 token 與登入狀態**已經寫進 store 了**。使用者看到的是自己已登入，但畫面上跟個人資料相關的區塊全是空的，而且沒有任何錯誤提示。

這類 bug 的共同特徵是**不報錯**：沒有例外、沒有紅字，只有一個說不出哪裡怪的畫面。要修的話，收尾動作該改成明確的 await 鏈，並在重試用盡時明確降級或回滾，不要留下這種中間態。

## 小結

如果只帶走三句話：

1. **伺服器端讀不到 `localStorage`，所以登入態必須有一份在 cookie** —— 但那份可以只是一個布林值，不必是 token。
2. **多個登入入口要匯進同一個保存點**，否則每加一種登入方式就多一個漏寫某層的機會。
3. **跨層寫入要原子化、非同步寫入要佇列化** —— 這兩件事修的都是「不會報錯」的那類 bug，而那類最難查。

至於 httpOnly 那一項：如果你正要開始設計，直接從伺服器端下發 httpOnly cookie 起步，會比之後再回來收斂省事得多。
